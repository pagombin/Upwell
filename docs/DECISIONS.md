# Decisions

Decisions made while building, with the reason for each. Newest last. Where a decision departs from the spec, it says so.

## D1. Branch
Work happens on `overnight-build`, branched from the Phase 0 branch `claude/new-session-agkd2d`. `main` is untouched.

## D2. Phase 0 amendments applied to the spec
All fourteen proposed changes from `docs/phase0/findings.md` are applied to `docs/spec.md` and cited inline as PC1 to PC14.

## D3. The origin gate compares against the final heartbeat, not the literal end position
The spec (PC13, cutover step 5) says the target's replication origin must reach the end position. Taken literally that produces false NO-GO verdicts: in Phase 0's passing runs (S09 quiet) the origin finished 56 bytes *below* the end position, because pgcopydb records the commit position of the last applied transaction while `--current` end positions include WAL written after it (the nudge, running-transaction records). Upwell therefore records the source WAL position immediately before writing the final heartbeat (`hb_before_lsn`) and requires `origin >= hb_before_lsn` after the drain. With writers stopped, the only transaction in that database after `hb_before_lsn` is the heartbeat itself, so passing this check means the heartbeat transaction (the last real write before the end position) was applied. The heartbeat row on the target is checked separately.

## D4. Data checksums are order-independent hash sums
Verification computes, per table and on both sides, `count(*)` and `sum` of the first 60 bits of `md5(row::text)` (as bigint, summed into numeric). It streams, needs no sort and no large memory, and detects missing, extra or changed rows. Tables are checksummed smallest first until `verify_checksum_budget_seconds` (default 600) is spent; the rest are reported as "not checksummed" (warning) and still get counts. A mismatch on any checksummed table is NO-GO.

## D5. Heartbeat table
`upwell.heartbeat(id bigserial primary key, kind text, token text, written_at timestamptz)` in a dedicated `upwell` schema, created on the source before the engine starts (so the clone copies it and the publication includes it). Cleanup drops the schema on both sides. Preflight checks the user can create it.

## D6. UI stack
React + TypeScript + Vite, embedded with `embed`, as the spec says. Departures, to keep the bundle small and offline-friendly and to fit tonight: plain CSS with design tokens instead of Tailwind/Radix, hand-written accessible components, and hand-written SVG charts instead of ECharts. The log viewer virtualizes rows itself.

## D7. Engine runner
Production uses the systemd template (PC1): `systemctl start upwell-eng@<instance>`. For development and the test suite in containers without systemd as PID 1, a `local` runner starts the engine detached (`setsid`), in its own cgroup v2 group when available (else its own process group), and stops it with SIGKILL to the whole group after 10 s, which mirrors the template's behavior. The runner is chosen by `engine.runner` in the config (`auto` picks systemd when PID 1 is systemd).

## D8. Store
SQLite in WAL mode through `modernc.org/sqlite` (pure Go). Metrics use the compact series-plus-samples shape (PC7).

## D9. The orchestrator calls the PostgreSQL check pack directly
Heartbeat, verification, discovery and target-database creation live in `internal/pgpack` and the orchestrator calls them through narrow functions. Engine-specific behavior (commands, sentinel, log parsing, slot release) stays behind the engine interface. A MySQL engine would come with its own pack; the orchestrator's calls are the seam.

## D10. The cutover waits for the final heartbeat to reach the target before setting end positions
Found in the first end-to-end run tonight: in one of two databases the final heartbeat, the last transaction before the end position, was never applied, while pgcopydb reported the end position reached. That is Phase 0's F9 (pgcopydb 0.18 drops the last transaction before an idle period when the end position arrives first). The gate caught it (NO-GO), but a GO path that depends on luck is not acceptable. The cutover now writes the final heartbeat, then writes a small "push" heartbeat row every 5 s until the final heartbeat is visible on the target, and only then sets end positions. (A logical-message nudge is not enough here: tonight's runs showed pgcopydb applies a transaction only after a later decodable transaction arrives, and pgoutput skips transactions without table changes. The logical message still serves its Phase 0 purpose of getting an idle stream past its end position.) The heartbeat's arrival proves every earlier write arrived; whatever pgcopydb drops after that is a nudge with no data. If the heartbeat does not arrive within the drain timeout (capped at 15 minutes), the cutover stops before setting end positions, streaming continues, and the operator sees why. Spec cutover step 3 amended accordingly. The origin check and data verification still run after the drain.

## D11. Target-database creation prefers template1; apply privileges are re-checked in the created database
Function grants are per database. Creating target databases from template0 dropped the replication-origin grants in the first test run, so the engine failed. Upwell now creates from template1 when its encoding and locale match the source (falling back to template0), and before launching the engine it re-runs the `target_apply_privileges` check inside the target database and refuses to start without the privileges (F2 would otherwise lose every change silently).

## D12. Verification ignores the `upwell` schema in table comparisons
The heartbeat table has its own checks (final heartbeat present, origin progress). Counting it as user data produced a confusing duplicate failure.

## D13. The built UI is committed under `internal/webui/dist`
`go build` embeds the UI. Committing the Vite output means the binary builds on a droplet (or in CI) without Node, and install.sh only needs Go or a prebuilt binary. `npm run build` regenerates it; the e2e suite always rebuilds before running.

## D14. Signed-out detection without a 401
The UI asks `GET /api/v1/auth/session` (public, 200 either way) on load instead of `GET /auth/me`, so the sign-in page loads with no failed network request or console error. `/auth/me` still returns 401 for API clients.

## D15. Same-origin framing is allowed
The Report screen shows the HTML report in an iframe from the same origin, so `frame-ancestors` is `'self'` and `X-Frame-Options` is `SAMEORIGIN` (was `'none'`/`DENY`). Other origins still cannot frame Upwell.

## D16. "Restart Upwell" works only under systemd
`POST /api/v1/system/restart` exits the process so systemd (`Restart=always`) brings it back; engines run in their own units and keep going. Without `NOTIFY_SOCKET` it refuses with a clear message instead of killing a server nobody will restart.

## D17. Plan estimates for connections and WAL
The plan review shows peak connections per side (concurrent databases × (table jobs + index jobs + engine sessions)) and WAL retained during the copy (current source WAL rate × copy time ÷ concurrency) when a rate has been measured; otherwise it says the rate is not known yet.

## D18. Lint policy
`golangci-lint` (v2, `standard` linters) runs clean with `.golangci.yml`. errcheck ignores best-effort calls with no useful handling (closing, removing temp files, writing to a client that left, single-row reads of optional facts, bookkeeping writes). State writes that decisions depend on (`setDB`, `saveFlags`, `refreshState`) log their own failures at error level, and the calls whose failure changes what happens next (stopping an engine the supervisor decided to stop, the disk guard, the drain nudge, the cleanup password file, the automatic restart's target reset) are now handled explicitly. staticcheck's quick-fix style suggestions (QF*) are off. Running staticcheck also showed that the catalog's `client_version` check was never emitted; it now runs (hard blocker when pg_dump or pg_restore is older than the source's major version).

## D19. Heartbeat alert threshold is 300 s, not 60 s
On an idle database pgcopydb 0.18 applies streamed changes in batches: in the e2e environment the newest heartbeat on the target trailed the source by 30 to 90 s with no backlog, which made the 60 s alert fire on every quiet database. The default is now 300 s. Cutover readiness does not depend on it (it uses the backlog), and the cutover pushes heartbeat rows until the final one arrives (D10).

## D20. UI verification is part of the build
`dev/e2e.sh` starts a fresh server, runs a real migration against the local clusters with a writer, seeds the demonstration fixtures (50 databases, 63-character names, more than 10 billion rows, more than 10 TiB, more than 7 days, long errors) and runs Playwright: every screen at 1440x900 and 1280x800 in both themes is screenshotted into `docs/screenshots` and must pass the overlap, clipping, horizontal-scroll and axe checks; every screen renders its loading, empty, error and stale states; cumulative layout shift on the live overview stays under 0.1; no console errors or failed requests; every control is reachable by Tab with a visible focus ring; viewers see no action buttons; and a small visual regression baseline (`web/e2e/__visual__`) catches unintended changes. Tables hide optional columns, last first, when they would otherwise scroll horizontally; the column chooser brings them back.

## D21. Engine unit failures carry systemd's reason
If an engine unit ends without success before pgcopydb logs an error (for example systemd cannot apply the unit's sandboxing or read its environment file), the database's error now includes systemd's `Result` and the unit's last three journal lines, so the operator sees the real cause instead of "the engine exited unexpectedly". install.sh adds the `upwell` user to `systemd-journal` for this. Needs a droplet to see in action.

## D22. The tester's walkthrough is automated
`web/e2e/flow.spec.ts` drives the README's test migration through the browser against the local clusters: the wizard from an empty form, a live connection test, preflight, start, In sync, stop and resume of the database, cutover to GO, verification, the report and cleanup. `dev/e2e.sh` runs it after the screen suite with the writer stopped. It found one real bug: a new migration's database list came back as JSON `null` and crashed the wizard; the API now never returns `null` for a list.

## D23. Roles are copied without passwords, as a non-superuser can
`pgcopydb copy roles` runs `pg_dumpall --roles-only`, which reads `pg_authid`, and only a superuser may read it: on DigitalOcean it always failed, so application roles were never created on the target and any `GRANT` to them in the schema could fail the restore. Upwell now dumps roles with `--no-role-passwords` (from `pg_roles`), skips platform and existing roles, turns off attributes only a superuser may grant (SUPERUSER, REPLICATION, BYPASSRLS), drops `GRANTED BY`, and applies the rest statement by statement. The event lists login roles created without a password; their passwords must be set on the target (for example in the DigitalOcean control panel) before applications switch.

## D24. Extensions are created on the target before the engine starts
The engine runs with `--skip-extensions` (a non-superuser cannot restore extension objects), and nothing created them, so a table using an extension type, function or operator (citext, hstore, pgcrypto, PostGIS) would fail its base copy. Upwell now creates every extension of the source database in the target database, in the same schema when it exists there, before launching the engine. Extension versions are the target's defaults.

## D25. A reused Idempotency-Key with a different request is refused
Keys now remember a hash of the method, path and body; the same key with a different request returns 422 `idempotency_key_reused` instead of replaying another request's answer (store migration 0002).

## D26. Engine failures during streaming are detected from the log (F13)
In the fidelity test a resumed engine hit pgcopydb's internal SQLite lock, logged a fatal error, and its apply process exited; pgcopydb's receive process ignores SIGTERM (F3), so the unit stayed active and the database showed In sync while nothing was applied for 15 minutes. The heartbeat gate turned that into NO-GO, so nothing was lost, but nothing recovered either. During streaming, a fatal engine line or an apply process that exits outside a cutover's end position now stops the unit and goes through the retry policy.

## D27. One automatic restart from zero for pgcopydb's internal lock during the base copy (F12)
pgcopydb's processes share a SQLite catalog; under load one of them intermittently fails with "database is locked" and the base copy fails. Because the copy had not finished, restarting it from zero is safe, so a database whose base copy failed this way restarts once automatically (under `auto_restart_base_copy_max_gb`); a second failure goes to Restart required.

## D28. Readiness also checks lag in time, and preflight checks the commit rate (F11)
pgcopydb 0.18 applied about 190 rows a second for a large transaction and about 5 transactions a second for small ones in the build container (TestApplyThroughput), while the target accepted 17,000 single-row inserts a second directly. A backlog under the byte threshold could therefore hide many minutes of apply time, and the database showed In sync while it was. The readiness gate now also requires each database's heartbeat lag to be under `cutover_max_lag_seconds` (180 s), so the write pause is bounded by how far behind the target really is, and preflight's new `apply_rate` check warns when a database commits more transactions a second than `assumed_apply_tps` (5, to be calibrated on a droplet).

## D29. The migration lock is keyed on the full ID
The API accepts a migration's full or short ID; the per-migration lock was keyed on whichever string the caller used, so an API client using the short ID was not mutually excluded with the supervisor. The lock now resolves the full ID first.

## D30. The drain nudge is a heartbeat row, not a logical message (F14)
With test_decoding, pgcopydb 0.18 cannot parse a logical decoding message and its receive process fails on it ("Failed to parse test_decoding message ... drain nudge"); Phase 0 had only proved the nudge with pgoutput. The nudge after setting end positions is now a one-row transaction in Upwell's own heartbeat table, which every plugin decodes; it falls after the end position, so it is never applied, and verification ignores the `upwell` schema (D12). The logical message remains only as the fallback for pgoutput when the heartbeat is off; with test_decoding and no heartbeat the nudge is refused with a clear message.

## D31. Log lines from before an attempt are never classified against it
The tailer resumes at its stored offset, so the last lines of a stopped run (for example "Apply process has terminated") could be read after the next attempt started and counted against it. Lines timestamped before the attempt began (by less than 30 minutes, so a clock or time-zone difference can never hide real errors) are now indexed but not classified. Stall detection (D26) also stays out of drains, where apply exiting at the end position is expected.

## D32. A target with no heartbeat at all counts as behind
Heartbeat lag was measured only once the target held at least one heartbeat row. When the target applied nothing from the start of streaming (F2 after a privilege was revoked), the lag condition read "Not measured yet" for ever, which blocked the cutover but gave no explanation. Lag is now measured from the oldest source heartbeat when the target has none, so the readiness gate says how far behind the target is. Found by the regression run (TestS02PrivilegeLostMidStream), which now checks both layers: readiness refuses the cutover, and an operator who raises the limit still gets NO-GO.

## D33. No startup parameters through a pooler; session state only on a pinned session
On the first droplet test the target (a DigitalOcean Advanced cluster, PostgreSQL 18 from Percona) sat behind a pooler that refused Upwell's `statement_timeout` startup parameter ("unsupported startup parameter", PgBouncer's wording); psql worked because it sends none. Two Upwell bugs made it worse: the error was explained as "the server did not answer in time" because the message contains the word "timeout", and the engine was started with `PGOPTIONS=-c synchronous_commit=off`, which PgBouncer refuses too, so pgcopydb could not have connected either. Now: a direct connection still gets the timeout as a startup parameter; an endpoint that refuses it is remembered and connected to without, and the timeout is then set with SET only after confirming that consecutive transactions reach the same server session, because in transaction pooling a SET would stay on a server connection the customer's application uses next. PGOPTIONS is gone: pgcopydb already sets synchronous_commit, maintenance_work_mem and the timeouts with SET in its own sessions, so the two settings that fed it (`target_synchronous_commit_off`, and `target_maintenance_work_mem`, which was never applied) are retired and ignored where stored. Tested with PgBouncer 1.22 in both modes (TestPoolerInFront) and a full migration through PgBouncer in session mode ending GO with identical data (TestMigrationThroughSessionPooler).

## D34. Transaction pooling is a hard blocker
pgcopydb sets session_replication_role and the replication origin once per session and keeps its snapshot in one transaction; behind a pooler in transaction mode those land on other server connections. The connection test and preflight (`session_pinning`, both sides) check that consecutive transactions reach the same backend while a second client connection holds a transaction open in between (a quiet pool would otherwise hand back the same server connection and hide transaction mode). Not pinned is a hard blocker; a client address that is not the droplet's own (a pooler or proxy, but sessions pinned) is a warning.

## D35. Session timeouts: only what pgcopydb does not override
pgcopydb clears statement_timeout and idle_in_transaction_session_timeout in every session it opens (copydb.h COMMON_GUC_SETTINGS, srcSettings, dstSettings), and pg_dump does the same, so the preflight blocker for a role with `idle_in_transaction_session_timeout = 1d` (seen on the droplet) was a false alarm. `session_timeouts` now reports those two as harmless and judges only idle_session_timeout, against three times the estimated base copy (at least 6 hours).

## D36. pgcopydb found on the PATH; systemd's notify socket kept from children
The droplet already had pgcopydb 0.18 from the PGDG package in /usr/bin, so install.sh reported it unchanged but nothing existed at the configured /usr/local/bin/pgcopydb. install.sh now links an existing pgcopydb there, and the app falls back to the PATH when the configured path is missing. Child processes inherited NOTIFY_SOCKET and systemd logged "Got notification message from PID ..., but reception only permitted for main PID" every few seconds; the app now removes NOTIFY_SOCKET and WATCHDOG_* from its environment at start and keeps the socket for its own watchdog.

## D37. Verification compares more, and fails closed on what it cannot compare
Bug bash 4 (an adversarial review of the gate) found ways verification could say GO with different data. Fixed: the row checksum hashed the bare alias `t`, which a column named `t` shadows, so only that column was hashed (now `ROW(t.*)`); descending sequences could never be "behind" and were never synced; indexes, constraints (including NOT VALID ones), triggers, views and functions were not compared at all, though the README said indexes were (now `schema_objects`, a blocker, plus NOT NULL, identity and generated expressions in each column's signature; NOT NULL rows of PostgreSQL 18's pg_constraint are left to the column signature so a 16 to 18 migration compares like with like); a large table outside both limits was "compared by estimates" that were never compared (now an empty or truncated target table is a blocker, and the message says what is not compared). Verification sessions now clear the role's timeouts, turn row_security off (a policy then raises an error instead of silently hiding rows), and fix TimeZone, DateStyle, IntervalStyle, extra_float_digits, bytea_output and lc_monetary so a row hashes the same on both servers. Other sessions' temporary tables are ignored everywhere (they caused false NO-GO and a false replica-identity blocker). Partitioned parents are sized by their partitions, so the checksum budget orders them correctly. Tests: TestVerifyCatchesWhatItMissed (each defect injected after the drain is named) and TestVerifyGOWithHardSchema.

## D38. Only a database whose engine reached its end position can be GO
End positions are set only when every database is streaming (in sync or catching up); otherwise the cutover stops before the point of no return and streaming continues. A database counts as drained only on the engine's own "end position reached" or a clean exit while draining (a new `drained` flag), not merely because its unit stopped without logging an error; databases that did not drain are stopped and get a "did not reach the end position" blocker. Abort and the move to end positions are one check-and-set on the migration's flags, abort cancels the cutover worker, and an aborted migration can neither get GO nor be marked switched.

## D39. Supervision never waits on a long operation
The supervisor took each migration's lock and so waited behind pause, abort, restart or cleanup, which hold it while stopping units one by one; with enough databases the loop's heartbeat went stale and the systemd watchdog would kill the app mid-operation. It now skips a migration whose lock is busy. Cleanup holds the lock for its whole run and clears pending automatic resumes first, so no resume restarts an engine whose slot is being dropped. Automatic restarts from zero are capped at three per database.

## D40. Login and setup are rate-limited; sessions end on password change
At most four Argon2id checks run at once (each takes 64 MiB) and each client address gets ten login or setup attempts a minute; failed logins are counted atomically, the dummy hash for unknown users uses the real parameters (no timing oracle), and a disabled or locked account is only revealed after the right password. Changing or resetting a password ends the user's other sessions. Idempotency keys are scoped per user and expire after a day. First-run setup creates exactly one admin and compares the token in constant time. The installer checks Go and the PostgreSQL client (17 or newer) against what the build and DigitalOcean's servers need, links the pgcopydb package's binary explicitly, backs up the store with sqlite3's online backup, and allows sshd's actual port before enabling ufw.

## D41. Row-level security that applies to the admin user is a hard blocker
pgcopydb copies with the admin user's own rights, so a table whose row-level security policies apply to that user (FORCE ROW LEVEL SECURITY, or a table it does not own, without BYPASSRLS) would be copied with only the rows the policies allow, silently. Verification already fails closed on it (row_security off makes the query error), but preflight now says so before anything is copied.

## D42. The engine version is read as packages report it
The PGDG package reports `pgcopydb version 0.18-1.pgdg24.04+1`. Preflight split that on dots, read the minor version "18-1" as 0, and hard-blocked the droplet's correct pgcopydb 0.18 as "older than 0.18". The version is now read as its leading major.minor; an unreadable version is a blocker that says so. The build container uses a source build ("0.18"), which is why the tests never saw this.

## D43. Restart from zero ends the engine's leftover sessions and cleans every object it restored
On the droplet (2026-10-11) Restart from zero failed twice with "dropping public.stock6 on the target: canceling statement due to statement timeout". When a target database also holds objects of its own (on Advanced, the platform's `doadmin.aries_*` table), the reset drops the source's relations one by one instead of dropping the database, and it ran with a 60 s statement timeout. The dead engine's server sessions (a COPY or index build keeps running on the target after its client is gone) still held locks, so the DROP waited until the timeout. Now the reset first terminates the engine's sessions in that database (pgcopydb names them `pgcopydb[pid] ...` and pg_dump and pg_restore inherit the name; only sessions of the same user), drops with no statement timeout but a 2-minute lock timeout, and names the lock holder if one remains. The table-by-table reset also left non-relation objects behind (types, functions, and the copy of the source's publication that pg_restore creates), so the next base copy failed with "publication ... already exists"; a launch that follows an earlier attempt now passes pgcopydb's `--drop-if-exists` (pg_restore `--clean --if-exists`), which drops exactly the objects in the source's schema dump and nothing else. Test: `TestRestartWithLeftoverEngineSession` (a session named like the engine's holds a lock on a table, the target database has an object of its own): before, 500 after 70 s; after, 200 in 10 s, the target-only table kept, and the database back in sync.

## D44. A failed attempt is explained by its root cause, and a lost connection says which side
The droplet's base copy failed because the target connection closed in the middle of a COPY (`[TARGET 0] SSL error: unexpected eof while reading`); pgcopydb's error handling then logged more errors, and Upwell showed the last one, "Failed to close snapshot ... on (null)", which pointed at the source snapshot instead. The log classifier now keeps each attempt's first error and recognises lost connections by pgcopydb's `[SOURCE n]`/`[TARGET n]` prefix; the reason shown says which connection was closed, during which table, and that something between the droplet and that cluster (a proxy or load balancer, a failover or a restart) ended it. Tests: `TestRootCauseOfDropletFailure` (the droplet's exact lines), `TestRootCauseFirstError`.

## D45. pg_dumpall connects to the maintenance database
Roles were not copied on the droplet: `pg_dumpall` ignores the database named in `--dbname` and connects to `postgres`, then `template1`, which DigitalOcean's pg_hba refuses. It now gets `--database <maintenance database>`. Test: `TestRolesDumpNamesTheMaintenanceDatabase`.

## D46. Supervision cannot be stalled by a slow cluster
The droplet's console was restarted by the systemd watchdog four minutes into the base copy (two `/healthz 503` then a restart), because supervision ticks took longer than the 90 s the health check allows. The likely cause is connections through the target's proxy while pgcopydb loaded it: every connection to a pooled endpoint also probed session pinning with a second connection, and each could wait up to 15 s to connect. The pinning result is now cached per endpoint for 10 minutes (the connection test and preflight still probe every time), each tick has a 50 s deadline, and a slow tick or step is logged with its name ("a supervision tick took 64s (slowest: ...)"), so the next occurrence says exactly what was slow.
## D47. Preflight fails closed: a check that could not run is a blocker
Audit finding 1 (commit 643e4c1): eight preflight queries discarded their errors and many more ignored `Scan` errors, so a query that timed out, lost its connection or was refused left an empty result and the check read OK. Evidence: `TestPreflightFailsClosed` runs preflight once per query (73 queries) and fails only that query through a test-only fault hook in `internal/pg` (`SetFaultHook`; every pgpack query now goes through `pg.QueryRow`, `pg.Query`, `pg.Exec` or `pg.QueryStrings`). Before the fix only 13 of the 73 failures produced a blocker; the rest reported OK (connect, primary, read_privs, replica_identity, row_security, dst_conflicts, extensions, the leftover slot, publication and origin checks, heartbeat_possible and others), reported a false reason (wal_level "is ''", repl_privilege "has neither REPLICATION"), or were downgraded to a warning or info (session_timeouts, target_disk, the seven count checks, the WAL sample, slot_wal_cap). Now every check runs its queries through a `probe` that records the first error, and a check whose query failed can only end as a blocker "Could not check: <error>" (hard when the check is hard, otherwise acceptable with a reason, like any blocker). Checks that share a query (the slots and WAL senders query, the WAL sample that feeds the throughput, apply-rate, slot-cap and staging checks, the target database lookup that feeds encoding and collation) inherit its error. `TargetApplyPrivileges` returns an error instead of reporting a failed query as a missing privilege, and the launch re-check refuses to start the engine when it cannot confirm the privileges. After the fix all 73 injected failures end as a blocker naming the failure. A connection failure to the target database during the conflict check is now a blocker too (it used to compare against an empty list).

## D48. The writers step sees open write transactions, fails closed, and verification resamples writes
Audit finding 2. `WriteActivity` ignored its query error, so two failed samples read 0 and 0, "no row changes". It counted `n_tup_ins + n_tup_upd + n_tup_del`, which PostgreSQL adds only when a transaction ends (and then within about a second), so a writer inside an open transaction was invisible and could commit after the end position. Evidence before the fix: `TestWritersOpenTransactionRefused` ended GO and its row was missing on the target; `TestWritesAfterVerificationNoGo` (a write after the data comparison) ended GO; `TestWritersCheckFailsClosed` (the statistics query fails) ended GO. Now any failed sample stops the cutover before end positions ("could not sample writes"); a client session holding a transaction ID (`backend_xid IS NOT NULL`, excluding Upwell's and the engine's sessions) counts as a writer and is named; the counter at the end of the writers step is stored per database (`writes_baseline`, store migration 0004) and a new verification check, `writes_stopped`, resamples it after each database's comparison: any change, any open write transaction, a missing baseline or a failed sample is a blocker. Upwell's heartbeat schema is excluded from the counter. After the fix all three tests pass with the reason named.

## D49. With an Admin override of detected writes, the resample decides the verdict
Audit finding 4. After an Admin overrode detected writes, verification compared a source that was still changing; a GO was possible if writes paused just before each table was read, and writes after verification were lost when applications switched. The override is still allowed (it is audited), but `writes_stopped` then says that the override was used and that the resample decides: any change since the writers step is NO-GO. Evidence: `TestOverrideWithWritesRunningNoGo` ended NO-GO before only by accident of timing (row counts), with no mention of the writes; it now ends NO-GO with the `writes_stopped` blocker naming the override.

## D50. Readiness conditions expire, and say how old their measurement is
Audit finding 3 and enhancement E6. The collector kept only each series' last value with no time, so when Upwell could not reach a cluster the heartbeat-lag condition kept its last good value and stayed green; a failed schema comparison kept the previous (possibly empty) result, and the schema condition even read green before any comparison had run. Evidence: `TestStaleReadinessTurnsRed` revokes CONNECT on the target database mid-stream (the engine's open apply connection keeps working); before the fix both conditions stayed green for the five minutes the test waited. Now every sample is timestamped; the lag condition fails when its measurement is older than three collection intervals (30 s at the default interval), and the schema condition fails when it has not run yet, when its latest attempt failed (with the error), or when it is older than three comparison intervals (3 minutes). Every measured condition states its age in its detail ("measured 8s ago") and in `sample_age_ms`. After the fix both turn red within about a minute, name the cause, and recover when access returns.

## D51. mode=offline is refused until offline migrations exist
Audit finding 5. The settings catalog accepted `mode = offline`, nothing read it, and the engine command always streamed (`--follow`), so a migration set to offline silently ran online. Evidence: `TestModeOfflineNeverIgnored` set it globally and per migration (both 200) and the plan still contained `--follow`. Now validation refuses it ("offline mode is not available in this version") on both paths, and Start refuses a migration that already has it stored. The test accepts either outcome that is not silent: refused, or an engine command without `--follow`, so it stays valid when offline mode is built (overnight item 2).

## D52. List checks report the true count and quoted names
Audit finding 7. `replica_identity` and `read_privs` reported the length of a sample capped at 100 or 50, and built names with `nspname||'.'||relname`, so a copied `ALTER TABLE` failed for mixed-case names. ## D64. Write freeze at cutover
Overnight item 1 (spec lines 61, 361, 371, 873). The cutover console offers the write freeze as the alternative to stopping writers by hand (Admins only, as the spec's routes say; off by default). Checked on PostgreSQL 16 before building: `ALTER DATABASE ... ## D80. Base copy progress is read without waiting on locks, in the background, and a failed read says so
On the droplet (2026-10-13) the target grew steadily for hours (the "Copied to the target" chart) while "Base copy in progress" nearly always said that no COPY or index build was running. Two causes, both found by reproducing it:
- **The progress query waited behind the engine's lock (a regression from D78).** pgcopydb copies a table that is not split by truncating it and copying it in one transaction, so each COPY holds an AccessExclusiveLock on its table until it ends (seen locally in `pg_locks` for every COPY session). The query now reads only the progress view (casting an oid to `regclass` takes no lock on the table), runs with `lock_timeout = 1s`, and reads the size only of split tables, whose COPYs do not truncate.
- **A failed read looked like an idle copy.** The progress was read inside the page's request (3 s to connect to the target, 6 s in all), and any failure, a connection timeout or a query error, produced an empty list shown as "No COPY or index build is running at this moment". The target was slow to answer all that evening (Upwell's own sampling of it took 10 to 50 s). ## D81. A failed base copy releases its slot; a crashed server process is told apart from a closed connection
- **The slot of a failed base copy is dropped.** On the droplet (2026-10-13) `migration_db` sat in Restart required with its slot holding 74.4 GiB of source WAL ("extended", and growing at the source's 45 MiB/s), because a failed base copy kept its slot until an operator restarted it. That slot can never be used: a base copy cannot resume, and Restart from zero drops it and creates a new slot at a new snapshot (`lifecycle.go`, engine `Cleanup`). Now, as soon as a base copy fails into Restart required, Upwell drops its slot, publication and origin (under the migration's lock, only while it still waits for a restart), and the supervision loop does the same every 5 minutes for any database in that state, which covers one that failed before this release. An event says how much WAL the slot held. With `max_slot_wal_keep_size` unlimited (as on that source) the held WAL could otherwise fill the source's disk.
- **A crash is not reported as "did not restart".** D78 compared `pg_postmaster_start_time()` with the attempt's start. When one server process is killed (as the out-of-memory killer does) or crashes, PostgreSQL ends every connection and reinitializes while the postmaster keeps running, so that time does not change (checked locally: after `kill -9` of a backend the log says "terminated by signal 9 ... all server processes terminated; reinitializing" and the start time is unchanged). The checkpointer is started again by that reinitialization, and its `backend_start` in `pg_stat_activity` is visible to non-superusers, so a checkpointer started after the attempt began (and more than a minute after the postmaster) is reported as "a server process crashed or was killed ... PostgreSQL ended every connection", with what to look for in the cluster's log. "Did not restart" now also says the server did not reset its connections.
Tests: `TestBaseCopyTargetConnectionClosed`, `TestBaseCopyTargetRestarted` and `TestBaseCopyTargetBackendCrashed` (the COPY's server process killed with signal 9: before, "did not restart"; now "crashed or was killed"), each also checking that the failed copy's slot is dropped (before: still there after 2 minutes) and that Restart from zero then reaches In sync.

## D83. The write freeze and the writes checks close five gaps; a read-only source is a preflight blocker
On the droplet (2026-10-14) Upwell reported writes frozen on the source while a sysbench TPC-C load kept running. ## D84. pgcopydb is built with a fix: it lost transactions that overlapped another one
Writing the pooled-load test above, the target ended with fewer rows than the source although the final heartbeat had arrived. Cause, in pgcopydb 0.18 and in its main branch as of 2026-10-14 (`ld_store.c`): after applying a transaction, the next one is chosen as "the first BEGIN at or after the last applied commit LSN", and the apply orders replay rows by BEGIN LSN while filtering them by commit LSN. A transaction's BEGIN carries its first LSN, which is lower than the commit LSN of any transaction that committed while it was open. So whenever transaction B began before transaction A committed and committed after it (any two concurrent writers), the one that committed first was skipped and never applied, silently: the replication origin and the heartbeat still advanced past it. Reproduced with pgcopydb alone (16 concurrent transactions: 15 or fewer reached the target, with pgoutput and with test_decoding) and through Upwell (`TestOverlappingTransactionsReachTarget`: ten rounds of "T1 begins and inserts; T2 inserts, updates and commits; T1 commits": the target missed all ten T2s, and verification ended NO-GO on exact row counts).
- **The fix** (`deploy/pgcopydb/0001-take-transactions-in-commit-order.patch`) takes transactions in commit order in both stages: the transform finds the next transaction by its COMMIT (or ROLLBACK) LSN after the cursor and the apply orders by commit LSN. With it, the test above passes (20 of 20 rows, GO) and so do the freeze tests under a 16-connection load.
- **The installer builds it.** `install.sh` now always builds pgcopydb from the v0.18 tag with the patches in `deploy/pgcopydb` (the packages lack the fix), with the version `0.18+upwell.1`, and rebuilds when the installed one reports anything else (never while an engine runs). `spikes/env/build-pgcopydb.sh` makes the same build for development; the integration tests and `dev/e2e.sh` take its path from `UPWELL_IT_PGCOPYDB` and `UPWELL_PGCOPYDB`.
- **Upwell refuses an unfixed engine for online migrations**: a hard preflight check `engine_commit_order` and the same check at each launch. Offline migrations apply no changes and are unaffected.
- **What this means for earlier migrations.** A migration run with the unfixed engine under concurrent writes may have missed transactions. Upwell's verification caught it wherever it compared exactly (row counts up to `exact_count_max_mb`, checksums within the time budget); a table larger than the exact-count limit and outside the checksum window was only checked for being empty or truncated, so it could have ended GO with rows missing. Compare such tables (counts, or `pgcopydb compare data`) before relying on a migration made before this build.
- Upstream: not yet reported; the patch and the reproduction are ready to send.

## D85. Bug hunt across the orchestrator and the API
An adversarial review of the whole application (2026-10-14) found these, each fixed:
- **An unreadable engine unit state was read as "exited" (O1).** `systemctl show` failing (a busy D-Bus, a timeout) returned an empty status, which supervision took for an engine that had stopped: it could restart from zero a base copy whose engine was still running, or mark a database failed. Supervision, startup reconciliation and a new launch now treat an unreadable state as unknown (skip, retry next pass, or refuse to start a second engine); stopping paths (restart from zero, cleanup, an undrained database at cutover) stop the unit anyway.
- **Launches ran inside the 50-second supervision tick (O2).** Creating the target database, extensions, privilege checks and roles on a slow cluster could exceed the tick's deadline and stop half-way. A launch now runs in its own goroutine (marked Preparing first, so it is never launched twice), waits for the migration's lock, and does nothing if the migration was paused, aborted or entered a cutover meanwhile. The automatic restart from zero after a base copy failure (F12) also runs outside the tick and keeps the database in Restart required until its reset succeeded (O5), so a console restart part-way never copies into a target that was not reset.
- **A stopped base copy kept its slot (O3) and the disk guard was unsafe (O4).** Only a base copy that failed with `base_copy_failed` released its slot (D81); a reboot, a failed launch or the disk guard left a slot holding source WAL. Any database in Restart required before its copy finished now releases it. The disk guard now stops one database every 2 minutes (it stopped one per evaluation, until none ran), under the migration's lock, never in a running cutover or a draining database, and a base copy it stops goes to Restart required (a Stopped base copy cannot resume).
- **Abort marked Stopped a database whose engine could not be stopped (O8)**; it is now Degraded with the reason, and Clean up stops it before removing anything. **Delete removed a directory that does not exist (O7)**, leaving every run directory; it now removes each database's and the roles copy's. A watched-table count slower than a minute piled up full scans (O6); one runs at a time per database. `supports()` read the engine's help text without its lock (O9), and an unreadable attempt count made a restart look like a first attempt (no DROP IF EXISTS).
- **API (A1 to A9).** Responses carrying a secret (a TOTP secret, recovery codes, a new API token) were stored in the idempotency table for replay; they are not stored any more (a repeated request answers that the secret is shown only once) and the stored ones are deleted (migration 0012). A 500 returned the raw error and was not logged; it is redacted and logged. TLS install and rollback are serialized, and a half-written pair falls back to the previous one at startup. `split_tables_larger_than` accepted any text (passed to pgcopydb as is; now auto, off or a size such as 50GB), and the disk warning threshold may not reach the critical one. Deleting a user revokes their API tokens. The sign-in failure said "locked" or "disabled" only for accounts that exist; it is one message now (the audit log keeps the reason). Operation idempotency keys were matched across migrations; they are scoped to the migration. An invalid setup time zone falls back to UTC.
- **D82 broke preflight on PostgreSQL 14 sources.** Its collation version query reads `pg_database.datcollversion`, which exists from PostgreSQL 15, so a PostgreSQL 14 source got an acceptable "Could not check" blocker that stopped the start (found by `TestVersionMatrix`, pg15 case: a 14 source to a 15 target). Before 15 the version reads empty and is not compared.

## D88. The droplet's firewall keeps long connections to the clusters
On the droplet (2026-10-14) the base copy of `migration_db` reached 97%, its best so far, only after the operator ran `sysctl -w net.netfilter.nf_conntrack_tcp_be_liberal=1` and `ufw allow proto tcp from <target ip> port 5432`. ## D91. Every row of a large table can be compared, and a verdict that rests on uncompared tables says so

## D99. pgcopydb creates a table's constraints after iterating its indexes (build 0.18+upwell.3)
After the D98 install (bundle `upwell-support-mfqv4x-20261015T195619Z`), the base copy of `migration_poc` failed four times in a row: at 15:14, 15:27, 17:30 and 17:50 UTC, each 8 to 20 minutes in. Every time the error was "Failed to execute statement: update summary set done_time_epoch = $1, duration = $2 where pid = $3 and conoid = $4 … [SQLite 5: database is locked] … Failed to iterate over list of indexes … Failed to create constraints for table public.<table>". Every time, no pgcopydb process logged anything for about 130 s first, not even the WAL stream process that otherwise reports every 10 s. The source then dropped the frozen stream ("could not receive data from WAL stream: SSL connection has been closed unexpectedly"). No network incident was involved this time.
- **Cause, in pgcopydb.** `copydb_create_constraints` created each constraint from inside `catalog_iter_s_index_table`, the catalog iteration over the table's indexes. That iteration holds the catalog semaphore and an open SQLite read for as long as `ALTER TABLE … ADD CONSTRAINT` runs on the target, and the hook writes the summary (`summary_add_constraint`, then `summary_finish_constraint`) from inside the loop. When the ALTER takes longer than the catalog's busy wait (2 minutes since upwell-2, D87), the summary update fails and so does the whole base copy. A primary key on a large table through the slow path to this target easily takes that long. D87's longer wait only moved the failure from 5 s to 2 minutes; it was the same failure. pgcopydb's main branch has the same code.
- **The fix** (`deploy/pgcopydb/0003-create-constraints-after-the-index-iteration.patch`): the iteration only collects the table's index OIDs. The constraints are created after it, each index read back with `catalog_lookup_s_index`. This is the pattern `copydb_queue_table_indexes` already follows ("now that we are no longer holding the catalog lock"). The build is now `0.18+upwell.3`. The three patches apply in order to a clean v0.18. Builds from upwell.1 on still pass the data-safety check (`engine_commit_order`); `install.sh` rebuilds an older engine when no engine unit runs.
- **Test:** `TestSlowConstraintDoesNotStallCopy` holds an ACCESS SHARE lock on the target's `orders` table from the moment one of its indexes is built. Its COPY and CREATE INDEX proceed and its ADD CONSTRAINT waits. It checks that `items` still gets its primary key meanwhile, holds the lock 150 s (longer than the catalog's wait), then requires In sync. With `0.18+upwell.2` the copy failed with the droplet's exact error ("update summary … conoid … database is locked … Failed to create index"). With `0.18+upwell.3` it reached In sync. The first version of the test took the lock as soon as the table existed; that blocked pgcopydb's TRUNCATE before COPY and tested nothing, and it was corrected before the before/after runs.

## D100. A started migration's connections can change, within limits
The operator asked whether the source or target connection can be edited after a migration starts, and for limits on when: never under a live migration. Until now the API refused every change once a migration started (`frozen`), the wizard was the only editor, and the migration page had none. That left no way to rotate a password, or to move to the target's private hostname as D98 recommends, without a new migration. Now `PUT /migrations/{id}/connections/{kind}` (and a **Connections** dialog on the migration page) applies these rules (`internal/orch/connchange.go`):
- **Before the start:** any change, as before.
- **A new password alone** (same host, port, user, database, TLS mode and CA): at any time, but only after Upwell connects with it (`conn_test_failed` otherwise, and the old one stays). Running engines keep their sessions; their next connection uses the new password.
- **The target's storage size alone:** at any time. Only the disk-space check uses it.
- **Anything else** (host, port, user, maintenance database, TLS mode, CA) changes where Upwell connects. That is allowed only with no cutover in progress and no engine running for any included database: neither a running state nor an active unit (`conn_busy`, with the running databases named). The new address must also reach the same cluster (`conn_other_cluster` otherwise). Same cluster means the same server start time, version, and oid and name of every database. If the old address can no longer be reached, the new one must hold this migration's replication slot (source) or origin (target). This covers the private hostname for the public one, a connection pool in front of the cluster, or a new address after a failover. Moving to another cluster would strand the slot on the old source, or the copied data on the old target; that needs a new migration.
- **Never after an abort, a clean up or a verdict** (`conn_frozen`).
The check and the change run under the migration's lock, so no launch or resume can start in between. Every change after the start is audited with the old and new endpoint, raises a `connection_changed` warning event, and resyncs the firewall rules (D88) for the new address.

Found by the test: pgcopydb records each database's bare source and target URIs (`user@host:port/dbname`) in its catalog (`schema/source.db`, table `setup`) and refuses to resume with others ("Catalogs … have been setup for Postgres source … and current source is …"). An address change therefore also has to update that record. The engine's new optional `Retarget` does it once the checks pass. It replaces only the user, host and port, keeping the rest of pgcopydb's recorded form, and touches nothing for a database whose engine never ran. If it fails, the old connection is put back and the change is refused (`conn_engine`). The clean up uses the same record, so it works after a change too.

Also fixed: the wizard saved a connection only when a password was typed, so a host change on its own was silently dropped; and it never prefilled the stored CA certificate, so saving again under verify-full lost it.

Tests: `TestConnectionChangeRules` covers these cases:
- While streaming, an address change of either connection (even to the same cluster through `localhost`) is refused with `conn_busy`.
- A wrong password is refused with `conn_test_failed`; the right one and a storage change are accepted, and the stream stays In sync.
- With the database stopped, the target moves to a PgBouncer in front of the same cluster and the source to `localhost`.
- A PostgreSQL 18 cluster is refused as `conn_other_cluster`.
- After the resume, a new source row reaches the target and PgBouncer's log shows the engine connecting through it.
- Events and audit are recorded, the clean up leaves nothing behind, and any change afterwards is `conn_frozen`.

Before the change, the test failed at its first assertion: every change was `frozen`. Before `Retarget`, the resume failed with pgcopydb's catalog error. `TestRetarget` checks the catalog rewrite on its own. The browser test "connections: only a password can change while engines run" opens the dialog on the streaming e2e migration. It checks that an address change is blocked with the running database named, and that a wrong password comes back refused.
While writing the test: a single row written to an otherwise idle stream reached the target after about 72 s, with or without a stop and resume. pgcopydb's apply waits on an idle stream. That is not a loss (the cutover sets its own end position), but it is why the test waits 3 minutes.

## D101. The engine's connections send keepalives; the support bundle keeps only the network data that explains this migration's failures
The 300 GB migration on the droplet (`mpaahv`, bundle `upwell-support-mpaahv-20261016T024631Z`, private hostnames on both sides, engine `0.18+upwell.3`) failed at 02:09:57 UTC on 16 October. Both CREATE INDEX connections died in the same second with "could not receive data from server: Connection timed out", on the two indexes of `public.stock7`. What the bundle shows:
- **Idle connections.** pgcopydb's two CREATE INDEX workers open their target connection when the copy starts, then wait for the first table to finish (`indexes.c`, `copydb_index_worker`). That took 9 m 40 s here. The socket samples show both connections with no byte sent or received from 01:50:16 to 01:59:57, and a keepalive timer of **119 minutes**: the kernel default.
- **No acknowledgement.** At 01:59:57 both sent their CREATE INDEX (93 and 106 bytes). Not one byte was acknowledged again: `bytes_acked` stayed at 1362 while the retransmission backoff climbed to 13. At 02:09:57, exactly the 600 s `engine_tcp_user_timeout_seconds`, the kernel gave up.
- **Reflected RSTs.** Every retransmission came back as an RST from the target's address. Each carried this droplet's own sequence number (518678486 = SYN 518677124 + 1362), its 106-byte TLS record and its timestamp, with source and destination swapped. Its TTL was 63, against 61 on the target's handshake: two hops nearer, next to the droplet. The target never sent them. A stateful device on the path (VPC gateway, cloud firewall or NAT) had forgotten both connections during their silence and bounced the next packets. The kernel ignored the RSTs because their sequence numbers were outside its window, so the connections hung until the user timeout. The COPY connections, busy throughout, were unaffected.
- **Why no keepalives.** pgcopydb defines keepalive defaults (`keepalives_idle=10`, `interval=10`, `count=60`, `copydb.c` `connStringDefaults`). It merges them only into the scrubbed URI it logs (`parse_and_scrub_connection_string`), not into the URI its workers connect with. So every pgcopydb connection used the kernel's 2-hour keepalive. The last migration succeeded because its first tables finished within 1.5 minutes. The bigger the tables, the longer the index workers sit silent.

Changes:
- **The engine URI carries `keepalives=1&keepalives_idle=10&keepalives_interval=10&keepalives_count=60`** (`pg.EngineURI`, unless already set). Every connection pgcopydb, pg_dump and pg_restore open now probes an idle peer every 10 s, which keeps the path's state for it alive. With a TCP_USER_TIMEOUT the kernel gives up on unanswered probes after it; without one, after 60 probes. `TestEngineConnectionsKeepAlive` reads the keepalive timer of every idle pgcopydb socket with `ss`. Before the change it found 119 min, as on the droplet; after it, at most 10 s.
- **A lost connection is recognised when libpq leaves out the side.** The timeout lines carried no `[TARGET]` prefix; only the next line (`[TARGET 0] connection pointer is NULL`) did. So no incident report was written, and the reason read only "Failed to get async query results". The side-less error is now attributed by the next prefixed line. The reason names the CREATE INDEX it was running ("while creating index fkey_stock_27 on public.stock7"). `TestRootCauseOfIndexConnectionTimeout` replays the droplet's lines.
- **The incident verdict recognises a reflected RST:** one from the peer's address whose sequence number continues this droplet's numbering, not the peer's (the report's tcpdump now runs with `-S`). It is reported as bounced by a device on the path, never as the cluster closing the connection. The first version compared against both ISNs with a fixed distance and misread one connection, whose peer ISN wrapped near ours; the nearer ISN now decides. A connection that stalled after being idle for a minute or more is reported with that idle time and what it means. `TestIdleThenReflectedRST` replays the droplet's packets and samples, addresses replaced.

## D103. The change apply no longer waits 100 ms per transaction or rescans its files (build 0.18+upwell.4)
During a one-hour sysbench TPC-C run on the droplet's source (16 threads, about 250 transactions a second, 300 warehouses), the source wrote about 38 MB/s of WAL, 137 GB in all. Upwell's backlog for `migration_db` reached 137 GB, and after the load stopped it drained at about 0.5 MB/s: about 76 hours. In the bundle (`upwell-support-mpaahv-20261016T174927Z`):
- The receive process read the replication stream at 30 to 40 KB/s, with 60 to 200 KB waiting unread in its socket buffer: pgcopydb, not the source or the network, was the limit.
- The apply kept up with the receive.
Locally, pgbench (8 clients, about 3,000 transactions a second) reproduced it: the apply ran at 5 to 7 transactions a second, which is finding F11. Traces of each process found four causes, all in pgcopydb 0.18:
- **A 100 ms wait before every transaction.** The apply loop's `select()` on the "receive done" pipe used a 100 ms timeout on every iteration, not only when idle, and each iteration applies one transaction. That alone caps the apply at about ten transactions a second.
- **Each "next transaction" lookup scanned the rest of the file.** In `output.db`, the query (from patch 0001) took the union of every COMMIT after the cursor, sorted it and kept one row: 28 ms a lookup on a file of 130,000 messages. In `replay.db` it filtered on `endlsn`, which had no index: 8.6 ms on 6,000 transactions. The cost grows with the backlog, so draining it is quadratic.
- **An fsync for every decoded message, twice.** Every message was inserted into `output.db`, then its transformed form into `replay.db`, each in its own SQLite transaction with `synchronous = FULL`. In 20 s the receive process made 17,184 fsyncs. That is cheap on this machine's disk (49 µs each), but on a droplet's disk it is likely what held the receive to a few hundred messages a second.
- **The receive process ignores SIGTERM**, as F3 already noted. This is not a performance problem; it is why stopping an engine needs the unit's kill.
Patch `0004-apply-without-waiting-and-cdc-files-without-fsync.patch`:
- The apply waits up to 100 ms only after a pass that found nothing to apply or transform. With work waiting it polls the pipe without waiting.
- Each lookup takes the first row of each branch in index order, then the smallest of those. That is the same row as before: `same rows: True` on real files for both queries; 0.18 ms and under 0.05 ms per lookup. `replay(action, endlsn)` gets an index, created on open (`if not exists`), so files written by an older build get it on the first restart.
- The CDC files (`output`, `replay`) use `synchronous = NORMAL`. That is safe because they are not the durable record. On restart pgcopydb streams again from the replication slot, which only advances to what the apply has committed on the target. In WAL mode, NORMAL keeps the file consistent; a power loss can only lose the last commits, which the slot sends again.
Result, same machine and workload (pgbench, 8 clients, 10 s, 18,819 transactions): **204 transactions a second applied** with upwell.4, against 5 to 7 with upwell.3, with the same rows on both sides. A 20-second load (31,244 transactions) applied at 154 a second: a larger backlog still costs more, so there is room for further work. With upwell.4, these pass: `TestOverlappingTransactionsReachTarget`, `TestP1LargeTransactions` and `TestP1WritersUnderBothPlugins` (both plugins), `TestResumeEndsStaleApplySession`, `TestRestartWithLeftoverEngineSession` and `TestHappyPath`. Preflight's new `engine_apply_rate` check warns about builds before upwell.4 (`TestEngineApplyUnthrottled`). `install.sh` rebuilds the engine when no engine unit runs.
What it means for the droplet: the backlog left over from the TPC-C run should drain much faster once the engine is rebuilt and `migration_db` restarted. A sustained TPC-C load is still at or above what one apply process can do (about 7,500 row changes a second at 250 transactions a second), so heavy write loads should pause before the cutover. When catching up would take far longer than a base copy, Restart from zero (D102 shows both numbers).

## D108. The apply confirms what the target committed (build 0.18+upwell.6); a pooler's kept session no longer holds the origin
The droplet, m33hv5, 2026-10-17. Two days into CDC, migration_db's apply failed with `cannot allocate memory for output buffer`. The next five resumes failed: first "replication origin with ID 1 is already active for PID 257476", then "cannot setup replication origin when one is already setup". Upwell then stopped retrying. Three faults, two of them in pgcopydb 0.18 itself.

**1. The apply never read the target's answers (data safety).** The apply connection runs in libpq pipeline mode, non-blocking, and the SQLite-based apply of 0.18 never sends a Sync or reads a result. Three consequences:
- A statement the target refuses is never seen. After an error the server ignores everything until a Sync, so the target silently stops applying.
- The send buffer holds everything the target has not read yet. On the droplet the target fell behind and the buffer reached libpq's 2 GB limit.
- `sentinel.replay_lsn` advanced with what had only been queued. The receive process reports it to the source as flushed. When the apply died, the source slot had been confirmed to 17C/A755A5A0 and the sentinel said 17C/E0106828, but the target's replication origin, which is the truth, was at 17C/5AEC10E8. The changes in between were only in the CDC file 0000017A. The engine's own cleanup deleted that file at the next start, because the sentinel said it was applied.

`TestApplyErrorStopsProgress` shows it on upwell.5: a duplicate key on the target, and the slot is confirmed past it with none of the 50 later rows on the target. That is silent loss. Upwell's verification at cutover would catch it as a count difference, and it held migration_db as Failed, but the engine must not report progress it has not made.

Patch `0006-confirm-the-apply-pipeline-and-publish-only-durable-progress.patch`:
- The pipeline is synced every 1,000 statements, 64 MB or 500 ms, inside large transactions too, and always before a keepalive, at endpos, and when the replay is drained. Any error stops the apply with the target's message. Upwell shows it, for example `[23505] ERROR: duplicate key value violates unique constraint "orders_pkey"`.
- replay_lsn is published only after the target has answered everything queued, and only once `pg_replication_origin_progress(origin, true)` has durably reached the last COMMIT. That is at most one query per sync. Until then the last confirmed position stays.
- Once the conflict was resolved, the resumed engine applied every row.
- `TestApplyQueueBoundedMemory` holds the target with a lock while 380 MB arrives in 30 transactions. upwell.5 grew by 384 MiB; upwell.6 grows by 21 MiB.
- One large transaction is still held in memory once by the transform: 380 MB in a single transaction cost about 400 MiB. That is bounded by the largest transaction, not the backlog.
- D106 was wrong to say the apply waits for each statement's reply. It never waited, and that was the bug.

**2. The CDC files opened with no busy timeout.** The receive and apply processes share the CDC files. A statement that met the other one's write failed at once with "database is locked", and the engine with it: for example the `create index if not exists` on a CDC file the receive process writes (D106), seen in one run of `TestResumeEndsStaleApplySession`. Patch `0007-wait-for-busy-sqlite-files.patch` sets a two-minute busy timeout on the output and replay files. `TestEngineWaitsForCDCFileLock` holds a write lock on the replay file for 8 s during a resume. It needed one automatic retry before the patch and none after.

A first version set the timeout on every catalog. Then the end-of-follow sequence step of `TestP1CutoverRestartAtEveryStep/pgoutput/writers` waited out the full two minutes on `source.db` in one run of three, and the cutover's drain timed out (NO-GO, safely). `source.db` keeps its own semaphore and retries (upwell.2); the droplet's "Failed to delete cdc_files row 2: database is locked" on it was only a warning. With the narrower patch the subtest passed 5 of 5.

**3. A pooler kept the origin.** The droplet's target connects through a proxy, with session pooling (preflight warned that `client_addr` was not the droplet). When an engine stops, the pooler keeps its server session for the next client. `DISCARD ALL` does not release a replication origin, and the session has lost its application name, so D89's clean-up of `pgcopydb[…]` sessions cannot see it. The next apply then gets either another server session ("already active for PID p") or that same one ("already setup"). `TestResumeFreesOriginHeldThroughPooler` (PgBouncer in session mode) shows a clean stop is enough to cause it.

Before each engine start, `pg.ReleaseOrigin` connects as the engine does and tries to set up the origin:
- "already setup": it resets the origin in that pooled session;
- "already active for PID p": it ends p, only if p is this user's session in this database;
- otherwise it resets the origin it took.

This repeats up to ten times. Event `origin_released` says what was done. The engine's cleanup does the same before dropping the origin.

**4. Changes gone means restart.** When the apply cannot open the CDC file its origin points into, and that file no longer exists, the class is `changes_lost`. The database goes to Restart required with an explanation and the event `changes_lost`. It no longer retries five times. Test: `TestClassify`.

**For m33hv5's migration_db:** the changes between 17C/5AEC10E8 and 17C/A755A5A0 exist nowhere any more: not on the target, not in the slot, not in a file. That database must restart from zero (Restart from zero, or Run again) after installing upwell.6. Nothing was applied out of order or skipped silently into a GO: it was held as Failed. migration_poc is unaffected, but runs the same engine. Its periodic stalls, recovered by the 10-minute restart (D90), fit the same pattern, so it should also be restarted on upwell.6 before a cutover is trusted.

**5. The drain no longer waits for the engine's own sequence step.** After "Follow mode is now done, reached endpos", pgcopydb's main process still copies the sequences through its catalog, and in about one run in four of `TestP1CutoverRestartAtEveryStep` it waited there for its full two minutes (upwell.2's catalog wait) with all changes applied. The drain waited for the unit to exit and timed out: a NO-GO. A draining database whose engine has logged its end position is now stopped and counted drained. Upwell syncs the sequences itself in the next step, and the origin and data checks still confirm the end position. `TestDrainDoesNotWaitForEngineSequenceStep` holds the catalog the moment the engine reports its end position: NO-GO before, GO after.

The readiness gate's "Migration is streaming" condition now also accepts a NO-GO from a cutover that set no end position (streaming continued). The cutover start already cleared such a verdict, but the gate waited for it to be empty, so neither the console nor `TestP1HeartbeatNeverThenLate` could start the second cutover.

A cutover's NO-GO now carries its cause in the operation's error ("verdict NO-GO for db: the final heartbeat did not reach the target …"), not only in the step log; `TestP1HeartbeatNeverThenLate` checks that.

Build `0.18+upwell.6` (`deploy/install.sh`, `pgpack.EngineBuildRequired`): Upwell refuses upwell.5 for new launches, so the installer rebuilds.

## D110. upwell.6 cut the apply rate by five sixths; upwell.7 syncs on the interval only
The droplet, m33hv5, 2026-10-19, TPC-C again on upwell.6: migration_db received 8–10 MiB/s of source WAL and applied 3.6 MiB/s, while the source wrote about 30 MiB/s.

| --- | --- |

| upwell.6 | 75 |
| upwell.7 | 510 |
